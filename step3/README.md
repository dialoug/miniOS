## Week 1：第一条观察

```bash
strace -e trace=write /bin/echo hello
```

可观察到 `write(1, "hello\n", 6) = 6`：参数分别是文件描述符、用户态缓冲区和请求写入的字节数，返回值是本次成功写入的字节数。`strace`展示的是系统调用边界，不能仅凭这一行断言内核内部经过了哪些函数；后续需要结合指定版本的源码与其他追踪工具建立调用图。

## Week 1：无效用户指针与错误返回

在 WSL2 上通过 `ctypes` 将地址 `0x1` 当作 `write()` 的缓冲区地址传入，`strace` 观察到 `write(1, 0x1, 6) = -1 EFAULT (Bad address)`；调用方获得返回值 `-1` 与 `errno=14`。这个实验说明系统调用参数中的指针仍指向用户地址空间，内核不能把它当作可信的内核指针直接使用。`EFAULT` 是这次调用的错误结果，不是实验进程因直接解引用 `0x1` 而收到的 `SIGSEGV`。

此处只记录可观察结果和系统调用契约；具体 `write()` 路径怎样访问用户内存，仍需绑定源码版本后追踪，不能由一条 `strace` 输出推断完整函数链。

## Week 1：有效地址也可能触发缺页异常

用 Python 创建 1024 页匿名映射，在 WSL2 上逐页首次写入。页大小为 4096 字节，`getrusage(RUSAGE_SELF).ru_minflt` 前后差值为 1051。这个进程级计数包含 Python 运行时的其他次缺页，不能把 1051 全部归因于那 1024 次写入；但它表明有效映射的首次访问也可能经过缺页处理，并在处理成功后继续执行。

不要把“缺页异常”直接等同于“非法内存访问”：有效但尚未建立所需页映射的地址可以由内核处理后重试；无效地址无法这样完成访问，用户程序直接访问时可能收到 `SIGSEGV`，通过系统调用传入无效用户指针则可能得到 `EFAULT`。具体结果还取决于访问方式与映射状态。

## Week 2：同步异常与外部中断

缺页异常由正在执行的内存访问指令触发，属于同步异常：同样的指令在同样的地址映射状态下会再次遇到同类问题。若内核能补齐有效映射，可以返回并重新执行触发异常的指令；若不能处理，用户程序可能收到信号。外部设备中断则来自当前指令之外的设备事件，发生时 CPU 可能恰好在执行任何程序或内核代码。两者都需要保存和恢复执行状态，但不能因此把它们视为同一种事件。

系统调用是程序主动请求内核服务的另一种受控入口；它也发生在执行 `syscall` 指令时，却不应与缺页等硬件异常或外部设备中断混为一谈。

在当前 WSL2 环境读取 `/proc/interrupts`，可以看到各 vCPU 的计数以及 `virtio`、`HYP`、`HVS` 等虚拟化相关条目。这些是累计计数，能证明本环境存在中断处理，但不能仅凭计数确定某次中断打断了哪条用户指令；也不能把 WSL2 的虚拟设备条目当作物理机硬件列表。

## Week 2：中断上下文与延后工作

硬中断处理程序运行在中断上下文，不能调用可能睡眠的操作；它通常先确认和处理紧急状态，再把较多工作交给后续机制。`request_threaded_irq()` 允许主处理程序唤醒 IRQ 线程，让线程部分处理可延后的工作。softirq 也用于延后处理，但仍属于不可随意睡眠的上下文；普通线程工作队列与 softirq/BH 工作队列的睡眠约束不同，不能只凭“工作队列”三个字判断。

本机 `/proc/softirqs` 可见 `TIMER`、`NET_RX`、`SCHED`、`RCU` 等各 vCPU 累计计数。它说明这些 softirq 类型曾被处理，不足以还原某个硬中断与某次 softirq 的一一对应关系。

## Week 3：虚拟映射与驻留内存

在 WSL2 上创建 16 MiB 匿名映射后，取得一个虚拟地址；随后用 `memset` 写遍整个区域。进程 `/proc/self/smaps_rollup` 的 RSS 从 11124 KiB 增至 27584 KiB，增加 16460 KiB，接近映射大小。RSS 是整个 Python 进程的汇总，因此多出的几十 KiB 不能归因于这块映射。实验支持的结论是：获得虚拟地址范围并不要求全部物理页当即驻留；实际访问后，驻留量可随之增加。

CPU 使用虚拟地址访问内存；TLB 缓存近期的地址翻译，未命中时依据页表寻找映射。TLB 未命中不等于缺页异常：页表中已有有效映射时，只需完成地址翻译；映射尚未就绪或访问权限不符时才可能进入缺页处理。当前尚未观察具体页表项或 TLB 事件。
